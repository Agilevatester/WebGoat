🎯 Challenge 1: Exploit SpEL Injection in MongoDB Queries

Difficulty: ⭐⭐⭐⭐

Scenario: A Spring Data MongoDB application uses `@Query` annotations with SpEL expressions to filter customer records. The application accepts user input for searching customers by first name. Your task is to discover if the query processor has unsafe behaviors when processing special SpEL patterns.

Objective: Craft a malicious SpEL expression that demonstrates how the query processor handles parameter substitution and can lead to code execution.

Challenge Completed!

Key Insight: The MongoDB query uses `@Query("{ 'firstName' : ?#{?0} }")` which evaluates SpEL expressions. What if you could inject special operators into the firstName parameter? Can you make the SpEL processor execute Java code?

🔍 Craft Your SpEL Expression:

💡 Hints to explore:

  • SpEL T() Operator: Access Java classes using T(classname) syntax
  • Runtime Access: T(java.lang.Runtime) gives access to system execution
  • Method Invocation: getRuntime() and exec() methods for command execution
  • Expression Pattern: Try T(java.lang.Runtime).getRuntime().exec('command')
  • Parameter Substitution: The firstName parameter is evaluated as SpEL via `?#{?0}` syntax

firstName 		This value will be evaluated as SpEL in the @Query annotation

ℹ️ What to Look For:

  • ✓ SpEL T() operator for class access
  • ✓ java.lang.Runtime class methods
  • ✓ exec() method for command execution
  • ✓ ProcessBuilder for alternative execution
  • ✓ java.nio.file for file system access

⚠️ Real-World Context:

In CVE-2022-22980, the vulnerability exists because Spring Data MongoDB evaluates user-supplied input as SpEL expressions when using `?#{?0}` syntax in @Query annotations. SpEL's T() operator allows access to arbitrary Java classes, including Runtime, ProcessBuilder, and file system classes. This allows direct execution of system commands with application privileges.
